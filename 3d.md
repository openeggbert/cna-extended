# Extending `cna-extended` with 3D Scenes — Analysis

Status: **DECISIONS RECORDED (2026-07-14) — analysis complete, implementation plan is in
[`plan3d.md`](plan3d.md), which still needs explicit phase-by-phase approval before any
code is written** (mirroring `plan.md`'s own original "DRAFT until approved" gate). This
document is the *analysis*; `plan3d.md` is the *phased task list* derived from it.

## 1. Purpose

`cna-extended` is currently a faithful, 1:1 C++ port of MonoGame.Extended, which is
**2D-only** — it has no concept of `Scene`, `World3D`, 3D `Camera`, or a 3D-aware
`SceneGraph` anywhere in its upstream C# source. This document analyzes whether and how
`cna-extended` could be extended with 3D scene support, based on a separate design study
(`cna_scene_/` — three brainstorming/specification notes; **unrelated** to the real,
much-smaller `cna-scene` sibling repository despite the similar name — do not confuse the
two) that sketched a `Scene` / `World` / ECS / `SceneGraph` / `Camera2D` / `Camera3D`
framework for a C++ XNA-style runtime.

The key constraint from the requester: **every new class, and every new method added to an
existing class, must have an identifier ending in `EXT`** (e.g. `Camera3DEXT`,
`GetWorld3DEXT()`). This distinguishes genuinely new, non-upstream additions from the
faithfully-ported MonoGame.Extended surface that makes up the rest of this codebase —
mirroring how `cna` itself already uses a `NOXNA` marker for its own non-XNA additions.

## 2. Source material studied

- `cna_scene_/cna-scene.txt`, `cna_scene_/monogame_extended.txt`,
  `cna_scene_/specification.txt` — three notes proposing a `Scene` / `SceneManager` /
  `Entity` / `Component` / `System` / `Camera2D` / `Camera3D` / `SceneGraph` / `World2D` /
  `World3D` / `RenderLayers` framework, with a concrete C++ specification (§3 below
  summarizes the concrete API shapes proposed there) and a self-audit listing known
  weaknesses (static/shared component storage, no dirty-flag optimization, `BasicEffect`-only
  3D rendering, no frustum culling, etc.). **This is the primary source for this analysis**,
  per the requester's explicit instruction.
- `cna-extended`'s own current source tree (this repository) — see §4.
- `cna` (sibling runtime) — confirmed to already provide `Model`/`ModelMesh`,
  `BasicEffect` (fully implemented, pixel-verified across all 3 backends, see
  `cna/docs/basiceffect-support.md`), `SkinnedEffect` (already implements
  `IEffectMatrices`/`IEffectLights`/`IEffectFog`, `MaxBones = 72`), `BoundingFrustum`
  (`Contains`/`Intersects` overloads for `BoundingBox`/`BoundingSphere`/`Vector3`/itself),
  `VertexBuffer`/`IndexBuffer`/`GraphicsDevice::DrawIndexedPrimitives`, `Vector3`,
  `Quaternion`, `Matrix` — i.e. every low-level 3D primitive this analysis's larger scope
  (§8) needs is already real and tested in `cna`, not hypothetical.
- `cna-scene` (sibling companion library) — read only to identify **already-implemented,
  reusable-as-reference** helper classes (`Camera3D`, `OrbitCamera`, `FollowCamera`,
  `CubeMesh`/`CubeMeshRenderer`, `BillboardMesh`/`BillboardMeshRenderer`, `TextureAtlas`,
  `DebugDraw`) — per the requester's decision (§6), these are a *source of implementation
  ideas*, the same role the real MonoGame.Extended C# source plays for the rest of this
  project's porting work, not a build-time dependency.

## 3. What the specification proposes

Condensed from `cna_scene_/specification.txt` (the most concrete of the three notes):

| Layer | Responsibility | Proposed shape |
|---|---|---|
| `Scene` | owns entities, systems, cameras, `World2D`/`World3D`; `Load`/`Unload`/`Update`/`Draw` lifecycle | class, one per game screen |
| `SceneManager` | switches the active `Scene` | thin wrapper, `SetScene` |
| `Entity` | an ID + typed component accessors | `AddComponent<T>`/`GetComponent<T>`/`HasComponent<T>` |
| `Component` | pure data (`TransformComponent`, `SpriteComponent`, `ModelComponent`, `CameraComponent`, `ScriptComponent`) | plain structs |
| `System` | logic over components (`RenderSystem2D`, `RenderSystem3D`, `ScriptSystem`) | `virtual Update`/`Draw` |
| `EntityRegistry` | per-component-type storage | `unordered_map<EntityID, T>` per `T` |
| `Camera2D` / `Camera3D` | view/projection matrices | position/zoom/rotation (2D), position/target/up/FOV (3D) |
| `SceneGraph` | parent/child transform hierarchy, world-matrix propagation | recursive `UpdateWorldTransforms` |
| `World2D` | `SpriteBatch`-based rendering, `RenderLayer` grouping | wraps `SpriteBatch` |
| `World3D` | `Model`/`BasicEffect`-based rendering | wraps `GraphicsDevice`/`Model` |

The specification's own self-audit (in `specification.txt`, §"AUDIT") flags real
weaknesses — `static` (not per-instance) component storage, no dirty-flag optimization in
`SceneGraph`, `BasicEffect`-only 3D rendering with no custom shader path, no frustum
culling, no component lifecycle hooks — and explicitly lists custom shaders, skinned
animation, and frustum culling as *future work*, not part of its own minimal core. The
requester's decision (§8) is to build these in from the start rather than defer them.

## 4. What `cna-extended` already has that maps onto this

This is the most important finding of this analysis: **`cna-extended` already implements a
large fraction of this specification**, built during the MonoGame.Extended port, under
different names, generally *more mature* than the specification's own sketch (the
specification's self-audit flags weaknesses that `cna-extended`'s existing code already
avoids). The new 3D layer **extends this existing infrastructure**, it does not duplicate it.

| Specification concept | Already exists in `cna-extended` as | Gap |
|---|---|---|
| `Entity` / `Component` / `System` / `EntityRegistry` | `CNA::Extended::ECS::World`/`Entity`/`EntityManager`/`ComponentManager`/`ComponentMapperOf<T>`/`Systems::*` (Artemis-style ECS, ported from MonoGame.Extended's own ECS module) | **None** for the ECS mechanics themselves. Already solves the specification's own flagged weakness: `ComponentManager`'s storage is per-`World` instance (a `Collections::Bag<ComponentMapper*>` member), not `static`/shared — multiple `World` instances are already safe. |
| `SceneGraph` transform hierarchy, world-matrix propagation | `CNA::Extended::Transform3` (`BaseTransform<Matrix>`), already ported from MonoGame.Extended's `Transform.cs` — parent/child via `setParentProperty()`, lazy dirty-flag-driven `getWorldMatrixProperty()`/`getLocalMatrixProperty()` recompute, `TransformBecameDirty`/`TranformUpdated` events | **None** for the hierarchy/dirty-flag mechanics — this already solves the specification's own flagged weakness ("no dirty flags → wasteful recompute"; `Transform3` already has them). Gap: `Transform3` is not yet an ECS *component* — nothing currently attaches one to an `Entity`. |
| `Camera2D` | `CNA::Extended::OrthographicCamera` (`Camera<Vector2>` + `IMovable`/`IRotatable`), fully ported, used throughout `Tilemaps::Rendering::*` | **None.** Already exists, already integrated with the rendering pipeline. |
| `Camera3D` | Nothing in `cna-extended`. `CNA::Extended::Camera<T>` (the abstract base `OrthographicCamera` derives from) is a generic template — `Camera<Vector3>` is a legal instantiation but has never been given a concrete subclass. | **Real gap.** See §5.1. |
| `Scene` / `SceneManager` lifecycle (`Load`/`Unload`/`Update`/`Draw`, switching) | `CNA::Extended::Screens::Screen`/`ScreenManager` (ported from MonoGame.Extended's `Screens/` module), plus `Transition`/`FadeTransition`/`ExpandTransition` | **Conceptual overlap, not identical.** `Screen` doesn't itself own an ECS `World` or a camera — see §5.7. |
| `World3D` (`Model`/`Effect`-based render system) | Nothing in `cna-extended`. `cna` (the runtime) already has real `Model`/`ModelMesh`/`BasicEffect`/`SkinnedEffect`/`VertexBuffer`/`IndexBuffer` support, already proven end-to-end by `Tilemaps::Rendering::TilemapRenderer` (a *2D* renderer that already uses `BasicEffect` + `VertexBuffer`/`IndexBuffer` + `GraphicsDevice::DrawIndexedPrimitives` — the exact same primitives a 3D renderer needs). | **Real gap**, but a narrow one: the low-level plumbing this needs is already exercised and working in this exact codebase for a different (2D) purpose. See §5.4/§5.6/§5.7. |
| Frustum culling | Nothing wired up in `cna-extended`, but `cna`'s `BoundingFrustum` (with `Contains`/`Intersects` against `BoundingBox`) already exists and is real, tested code. | **Real gap**, narrow — needs an ECS bounds component + a culling pass in the render system, not new math. See §5.6. |
| `RenderLayers` (2D) | `CNA::Extended::Tilemaps::Rendering::RenderMode`, and layer/depth sorting throughout `SpriteBatch` usage | **N/A for 3D** — 2D layers don't need translating; 3D wants its own opaque/transparent pass grouping instead (folded into §5.4). |
| `ScriptComponent` (raw function-pointer callbacks) | Nothing directly equivalent; `CNA::Extended::Animations::AnimationEventTrigger` and various `EventHandler<T>`-based hooks cover related but narrower needs. | Out of scope for this analysis — scripting is orthogonal to "3D scenes" specifically. |

## 5. Recorded decisions

Resolved by the requester on 2026-07-14 (superseding the open questions this document
originally raised):

1. **Reuse mechanism**: `cna-scene` is a **reference source, not a build dependency**.
   Needed logic (camera math, cube/billboard geometry, etc.) is read, understood, and
   **re-implemented as `cna-extended`'s own `EXT`-suffixed code**, the same relationship
   this whole project already has with the real MonoGame.Extended C# source — read it,
   port/adapt it faithfully, land it as this project's own code, credit it in `NOTICE.md`
   if license terms require it (`cna-scene` is MIT-licensed, same family as this project;
   confirm attribution needs per file when this is actually implemented). **No new CMake
   dependency, no new sibling link.**
2. **Namespace**: `CNA::Extended::World3DEXT` (not `Scene3DEXT` — matches the
   specification's own `World3D` terminology, and reads naturally next to this project's
   existing `CNA::Extended::ECS`, `CNA::Extended::Tilemaps` sub-namespace pattern).
3. **Tracking**: a new standalone document, [`plan3d.md`](plan3d.md) — *not* a reopened
   `plan.md` Phase 11, since `plan.md` was explicitly scoped and approved for "port
   MonoGame.Extended" (a 2D-only library), a scope that is now 100% complete and should
   stay closed as a historical record.
4. **Scope ceiling for the first version**: **larger scope, not the specification's own
   minimal core.** Frustum culling, a custom shader pipeline (not `BasicEffect`-only), and
   skinned/skeletal animation are all **in scope from the start**, not deferred — see §8's
   phase list, which folds these into the initial implementation rather than treating them
   as later follow-ups the way the specification's own audit does.

## 6. Proposed `World3DEXT` classes

Everything below is new — none of it exists in upstream MonoGame.Extended, so every
identifier gets the `EXT` suffix per the naming rule in §7. File layout follows the
established `include/CNA/Extended/World3DEXT/<Type>.hpp` /
`src/CNA/Extended/World3DEXT/<Type>.cpp` pattern (matching `Tilemaps/`, `Particles/`,
`ECS/`'s existing per-module layout).

### 6.1 `Camera3DEXT`

**Correction made before implementation (2026-07-14), recorded for transparency**: this
document originally proposed `Camera3DEXT : Camera<Vector3>, IMovable, IRotatable`,
reasoning that reusing the existing generic `Camera<T>` base would avoid a "parallel type"
duplication. Reading the actual headers before writing code showed this was wrong:
`Camera<T>`'s interface only uses `T` for `Position`/`Origin`/`Center` — half of it
(`getBoundingRectangleProperty() -> RectangleF`, `Contains(const Vector2&)`,
`Contains(const Rectangle&)`) hardcodes genuinely 2D types **regardless of `T`**,
because upstream MonoGame.Extended's `Camera<T>` was never actually instantiated with
anything but `Vector2` — the template parameter is vestigial, not a real 2D/3D
abstraction. `IMovable`/`IRotatable` are flatly 2D too (`Vector2 getPositionProperty()`,
a single `float` rotation angle — no `Quaternion`). Forcing `Camera3DEXT` into any of
these three would require implementing nonsensical methods (`Contains(Vector2)` on a
perspective camera; a `RectangleF` "bounding rectangle" for a 3D frustum). **Corrected
design**: `Camera3DEXT` is a standalone class, matching `cna-scene::Camera3D`'s own
(already correct) shape — position, target-or-forward, up, FOV, aspect ratio, near/far
planes, `GetViewMatrixEXT()`/`GetProjectionMatrixEXT()`/`GetBoundingFrustumEXT()`. No
existing base class is reused here because none of the three candidates actually fit a
3D camera despite surface appearances — this is a genuine gap, not a missed-reuse
opportunity.

```cpp
namespace CNA::Extended::World3DEXT
{
    class Camera3DEXT final
    {
    public:
        [[nodiscard]] Vector3 getPositionProperty() const;
        void setPositionProperty(const Vector3& value);
        [[nodiscard]] Vector3 getTargetProperty() const;
        void setTargetProperty(const Vector3& value);
        [[nodiscard]] Vector3 getUpProperty() const;
        void setUpProperty(const Vector3& value);
        [[nodiscard]] float getFieldOfViewProperty() const;   // radians
        void setFieldOfViewProperty(float radians);
        [[nodiscard]] float getAspectRatioProperty() const;
        void setAspectRatioProperty(float value);
        [[nodiscard]] float getNearPlaneProperty() const;
        void setNearPlaneProperty(float value);
        [[nodiscard]] float getFarPlaneProperty() const;
        void setFarPlaneProperty(float value);

        [[nodiscard]] Matrix GetViewMatrixEXT() const;
        [[nodiscard]] Matrix GetProjectionMatrixEXT() const;
        [[nodiscard]] Microsoft::Xna::Framework::BoundingFrustum GetBoundingFrustumEXT() const;
    };
}
```

### 6.2 `Transform3ComponentEXT`

The ECS bridge `Transform3` itself doesn't provide: an ECS component wrapping (or
embedding) a `Transform3`, plus a parent *entity ID* (not just a parent `Transform3*`) so
scene-graph hierarchy can be expressed in terms of `Entity`s, matching the specification's
`TransformComponent.parent`/`.children`.

```cpp
namespace CNA::Extended::World3DEXT
{
    struct Transform3ComponentEXT
    {
        Transform3 TransformEXT;    // reuses the existing, dirty-flag-optimized type as-is
        int ParentEntityIdEXT = -1; // -1 = no parent
    };
}
```

### 6.3 `TransformHierarchySystemEXT`

A small ECS system that walks every `Transform3ComponentEXT`, resolves
`ParentEntityIdEXT` to the parent entity's own `Transform3ComponentEXT.TransformEXT`, and
calls the existing `Transform3::setParentProperty()` to wire the *real* hierarchy — after
which `Transform3`'s own existing dirty-flag machinery handles all propagation with no
further new logic needed. This is a thin adapter, not a new hierarchy implementation
(matching the specification's own audit note: don't re-invent dirty-flag propagation,
`Transform3` already has it).

### 6.4 `ModelComponentEXT` + custom shader pipeline

Per the recorded larger-scope decision, this is not `BasicEffect`-only: the component
holds a non-owning `Effect*` (the real polymorphic base, matching `cna`'s own
`Effect`/`BasicEffect`/`SkinnedEffect`/custom-`ShaderEffect` hierarchy — see
`DefaultEffect.hpp`'s established precedent in this codebase for a hand-authored
`ShaderEffect` subclass), so callers can supply `BasicEffect`, `SkinnedEffect`, or a fully
custom `ShaderEffect` interchangeably. `RenderSystem3DEXT` (§6.6) only needs to know how to
set `World`/`View`/`Projection` — every one of `cna`'s effect classes already implements
`IEffectMatrices` for exactly this reason, so no per-effect-type branching is needed for
the matrix-setting path; effect-specific setup (texture, lighting, bones) is the caller's
responsibility when constructing the component, matching how `TilemapRenderer` already
lets its caller substitute a custom `BasicEffect` instance (see that class's own header
comment on the `Effect`-narrowing precedent).

```cpp
namespace CNA::Extended::World3DEXT
{
    struct ModelComponentEXT
    {
        Microsoft::Xna::Framework::Graphics::Model* ModelEXT = nullptr; // non-owning,
        Microsoft::Xna::Framework::Graphics::Effect* EffectEXT = nullptr; // matches this
        Microsoft::Xna::Framework::BoundingSphere BoundsEXT;             // project's
    };                                        // externally-owned-GPU-resource convention
}
```

### 6.5 `SkinnedModelComponentEXT`

A distinct component (not a flag on `ModelComponentEXT`) for animated models, since
skinned rendering needs real additional per-frame state (bone transform array, up to
`SkinnedEffect::MaxBones == 72`) that a static model never carries — keeping it a separate
component avoids paying that cost for every entity, matching this project's established
"don't add fields nothing needs" discipline.

```cpp
namespace CNA::Extended::World3DEXT
{
    struct SkinnedModelComponentEXT
    {
        Microsoft::Xna::Framework::Graphics::Model* ModelEXT = nullptr;
        Microsoft::Xna::Framework::Graphics::SkinnedEffect* EffectEXT = nullptr; // owning or
        std::vector<Matrix> BoneTransformsEXT;                                    // non-owning
    };                                                    // TBD at implementation time (§9)
}
```

An `AnimationSystem3DEXT` (advances bone transforms per frame, likely reusing this
project's already-ported `Animations::AnimationController` timing/frame-advance logic
where the shape fits, rather than re-inventing frame timing) would own the actual
skinning-animation playback logic; `RenderSystem3DEXT` only needs to read the resulting
`BoneTransformsEXT` array and forward it to `SkinnedEffect`.

### 6.6 `RenderSystem3DEXT`

An ECS `Systems::EntityDrawSystem`-derived system (reusing the existing `Systems::`
infrastructure, not a parallel one). Per frame:

1. Build (or reuse) `Camera3DEXT::GetBoundingFrustumEXT()`.
2. For each entity with `Transform3ComponentEXT` + (`ModelComponentEXT` or
   `SkinnedModelComponentEXT`): test `BoundsEXT` (transformed by the entity's current
   world matrix) against the frustum via `BoundingFrustum::Contains`/`Intersects`; skip
   entities that test `Disjoint` — this *is* the frustum-culling requirement, built from
   `cna`'s existing, real `BoundingFrustum`, not new math.
3. For surviving entities: set `World`/`View`/`Projection` on the entity's `Effect*` (via
   `IEffectMatrices`, one code path for every effect type — see §6.4), then draw via the
   same `VertexBuffer`/`IndexBuffer` + `Effect::Apply()` + `DrawIndexedPrimitives` pattern
   `TilemapRenderer.cpp` already uses successfully in this codebase.

```cpp
namespace CNA::Extended::World3DEXT
{
    class RenderSystem3DEXT final : public ECS::Systems::EntityDrawSystem
    {
    public:
        explicit RenderSystem3DEXT(Camera3DEXT& camera);
        void Draw(ECS::World& world, const GameTime& gameTime) override; // matches
    };                                       // EntityDrawSystem's real virtual signature;
}                                     // this whole class/its ctor/fields are the new EXT surface
```

### 6.7 Cube / billboard / debug-draw helpers (re-implemented, not linked, per §5.1)

Ported/adapted from `cna-scene`'s existing `CubeMesh`/`CubeMeshRenderer`,
`BillboardMesh`/`BillboardMeshRenderer`, and `DebugDraw` as reference material (read their
real, working implementation for the geometry/UV/draw-call logic, then re-author as this
project's own code, matching the same "port faithfully, land as our own" relationship this
project has with real MonoGame.Extended):

- `CubeMeshComponentEXT` / `CubeMeshRenderSystemEXT`
- `BillboardComponentEXT` / `BillboardRenderSystemEXT`
- `DebugDrawComponentEXT` / `DebugDrawSystemEXT`

### 6.8 `World3DScreenEXT` — recommend reuse of `Screen`, not a new `Scene` type

The specification's `Scene`/`SceneManager` maps closely enough onto the already-ported
`CNA::Extended::Screens::Screen`/`ScreenManager` that inventing a parallel type would be a
duplication, not an extension — the same "reuse, don't re-roll" judgment this project has
applied repeatedly (e.g. `sharp-runtime`'s `ObservableCollection`,
`Dictionary::GetValueOrDefault`).

```cpp
namespace CNA::Extended::World3DEXT
{
    // A Screen subclass, not a competing Scene type -- reuses Screen's real
    // Load/Update/Draw/Unload lifecycle and ScreenManager's existing stack/transition support.
    class World3DScreenEXT : public Screens::Screen
    {
    public:
        [[nodiscard]] ECS::World& GetWorld3DEXT();
        [[nodiscard]] Camera3DEXT& GetCamera3DEXT();
    };
}
```

## 7. Naming convention (as requested)

- Every genuinely new class/struct/enum: name ends in `EXT` (`Camera3DEXT`,
  `Transform3ComponentEXT`, `RenderSystem3DEXT`, `SkinnedModelComponentEXT`).
- Every genuinely new **method added to an existing (already-ported) class**: name ends
  in `EXT` (e.g. if `Screens::Screen` ever needs a new convenience accessor rather than a
  new derived class, it would be named e.g. `GetCamera3DEXT()`, never a name that could be
  confused with a literal MonoGame.Extended member).
- Members that **override** a real base-class virtual (e.g. `RenderSystem3DEXT::Draw`,
  overriding `EntityDrawSystem::Draw`) keep the base method's real name — the `EXT` suffix
  marks the *type* as new, not every inherited/overridden member name, since renaming an
  override would break the virtual dispatch contract it exists to satisfy.
- Namespace `CNA::Extended::World3DEXT` is itself suffix-marked for the same reason,
  mirroring `cna`'s own `NOXNA` convention for "this is a real addition to this codebase,
  not a literal port of anything."
- Existing, already-ported identifiers (`Transform3`, `World`, `Entity`,
  `OrthographicCamera`, `Screen`, …) are **not** renamed or retrofitted with `EXT` — the
  suffix marks *new* surface only.

## 8. Phasing

See [`plan3d.md`](plan3d.md) for the authoritative, checkbox-tracked phase list. Summary:
Phase 1 (`Camera3DEXT`) → Phase 2 (`Transform3ComponentEXT` +
`TransformHierarchySystemEXT`) → Phase 3 (`ModelComponentEXT` + `RenderSystem3DEXT`,
including frustum culling and the multi-effect pipeline from day one, per §5's recorded
scope decision) → Phase 4 (`SkinnedModelComponentEXT` + skinned animation) → Phase 5
(`Collisions3DEXT`, a 3D counterpart of `Collisions2D`) → Phase 6 (`Graphics3DEXT`, a 3D
counterpart of `Graphics` — absorbs cube/billboard/debug-draw helpers, §6.7, plus
animated billboards and 3D text) → Phase 7 (`Particles3DEXT`, a 3D counterpart of
`Particles`) → Phase 8 (`Tilemaps3DEXT`, a 3D/voxel counterpart of `Tilemaps`) → Phase 9
(`World3DScreenEXT`). Phases 5-8 were added after a follow-up scope-expansion decision
(2026-07-14, same day as the rest of §5) — the owner confirmed these four specific 2D
modules should get systematic 3D counterparts; other 2D-only modules (`NinePatch`,
`Tweening`, `ViewportAdapters`, `Timers`, `BitmapFonts`, `Input`) were not selected and
stay out of scope unless asked for later.

## 9. Remaining open questions

A few implementation-detail questions are deliberately left for `plan3d.md`'s own
per-phase approval step rather than answered here, since they don't change this
document's overall design:

1. **RESOLVED (Phase 4, 2026-07-14)**: `SkinnedModelComponentEXT::EffectEXT` ownership —
   non-owning `SkinnedEffect*`, one instance per animated entity, confirmed correct by
   reading `AvatarRenderer::DrawRealEXT`'s real, already-working usage
   (`AvatarRenderer.cpp`): a single `SkinnedEffect` is shared across a whole model's
   `Parts`, not per-`ModelMeshPart` — see `plan3d.md`'s Phase 4 entry for the full
   reasoning. Also discovered during this phase: `cna` already has a complete, real
   `SkinnedModelEXT`/`AnimationClipEXT`/`BoneTrackEXT`/`KeyframeEXT` type family
   (`cna/include/Microsoft/Xna/Framework/Graphics/SkinnedModelEXT.hpp`, built for
   `AvatarRenderer` but avatar-agnostic in its actual bone-sampling logic) — reused
   directly rather than re-implemented, so `SkinnedModelComponentEXT` wraps
   `SkinnedModelEXT*`, not a hand-rolled bone/skeleton type.
2. Exact license-attribution mechanics for code adapted from `cna-scene` (§5.1) — likely a
   `NOTICE.md` entry per adapted file, matching this project's existing pattern for
   code derived from other MIT-licensed projects (SlimMath/`Angle.hpp`,
   nickgravelyn's Triangulator, artemis_CSharp's `Bag<T>`) — confirm the exact wording
   when Phase 6 (the phase that actually adapts `cna-scene` code, per the Phase 5-8 scope
   expansion recorded in `plan3d.md` §2) lands adapted code.
3. **RESOLVED (Phase 4, 2026-07-14)**: `AnimationSystem3DEXT` is a new, dedicated system,
   not an extension of `Animations::AnimationController` — that class's discrete
   fixed-duration-per-frame sprite-sheet timing model doesn't fit continuous keyframe
   interpolation across arbitrarily-spaced `TimeSpan`-keyed keyframes, which
   `SkinnedModelEXT::ComputeBoneTransformsEXT` (see point 1) already implements
   correctly — `AnimationSystem3DEXT` is a thin per-entity driver over it, not a new
   timing engine. See `plan3d.md`'s Phase 4 entry.
